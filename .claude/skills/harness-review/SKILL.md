# harness审查（Harness review）

harness是这个仓库里一切塑造智能体如何工作的东西：它所读的文件、它所遵循的规则、
那些抓住它的检查。它有两半。指南（guide）在智能体行动之前陈述要求。传感器
（sensor）在行动之后检查结果。两者都不可或缺，而同一条规则往往两边都该有。

## 层级（Layers）

每一项资源都是按它进入上下文窗口的时机来放置的。越靠后的层级消耗的上下文越少，
约束力也越强。

| 层级 | 存放于 | 进入上下文的时机 | 属于哪一半 | 强度 |
|---|---|---|---|---|
| L0 | `/AGENTS.md` | 每个会话，在任务尚未可知之前 | 指南 | 请求 |
| L1 | `<component>/AGENTS.md`、`<component>/POSTMORTEM.md`、`.claude/rules/` | 当那条路径被触及时 | 指南 | 请求 |
| L2 | `.claude/skills/<name>/SKILL.md`，外加 `references/` | 描述始终进入，正文在被判定相关时进入 | 指南 | 请求 |
| L3 | `.claude/agents/<name>.md` | 在一个独立的窗口里；只有一份摘要返回 | 指南 | 请求 |
| L4 | `.claude/settings.json` 里的 hook | 从不进入；在某个事件上运行 | 传感器 | 保证 |
| L5 | `tools/checks/`、审查类 skill、CI | 从不进入；只有失败才返回 | 传感器 | 保证 |

预算。L0：整个文件 200 行。L1 AGENTS.md：每份 150 行。L2：描述约 100 个
token，正文不超过 5k token，`references/` 不设上限。POSTMORTEM.md 是仅追加
（append-only）的；超过大约 1000 行后加一个症状索引。

## 放置（Placement）

对每一块知识问两个相互独立的问题。重要的规则两个都答得上。

作为指南，它该归属何处？

| 它承载的是…… | 层级 |
|---|---|
| 无处不在、适用于每个任务、且无法从代码推断出来 | L0 |
| 只在某一个目录内、或只针对某一种文件类型 | L1 |
| 只在运行某个可重复流程期间 | L2 |
| 只在一个其产出没人会读第二遍的任务内部 | L3 |
| 哪儿都不特别属于 | 把它略去 |

代码能否强制执行或验证它？

| 那就再加上 | 层级 |
|---|---|
| 一个在该动作绝不允许发生时将其拦截的 hook | L4 |
| 一个在程序能够裁决时对结果做判定的脚本 | L5 |
| 什么都不加——当只有模型才能裁决时 | 让它保持推断性（inferential） |

把一条规则从自然语言挪成一个 hook 或一个脚本，是你能提议的、价值最高的改动。
自然语言是一个请求；代码是一个保证。

在写下任何一行之前，先做两项测试：

- 删除测试。如果这一行被删掉，智能体会不会犯错？如果不会，就别写它。
- 不变量测试。这一条到下个月是否仍然成立？诸如逐特性计划（per-feature plan）
  之类的意图快照，属于harness之外。

## 那五个章节

`/AGENTS.md` 和每一份 `<component>/AGENTS.md` 都使用同样的五个章节，只在缩放
层级上有所不同，如同 C4 模型：根文件是「上下文（context）」视图，组件文件是
「容器（container）」视图。

| 章节 | 根文件 | 组件文件 |
|---|---|---|
| 产品 | 每个组件用一句话 | 详细描述本组件 |
| 技术 | 技术栈；无法从 manifest 猜出来的命令 | 本组件特有的工具 |
| 结构 | 各组件如何关联 | 内部构造、状态机、时序 |
| 目录地图 | 每个顶层目录一行：它的用途、它自己的 AGENTS.md 在哪 | 每个子包（subpackage）一行 |
| 约定 | 与语言默认做法不同的选择 | 同上，但限定在此范围内 |

目录地图是语义加指针，绝不是一份文件清单。智能体自己能跑 `ls`。

## 生长（Growth）

| 触发条件 | 动作 |
|---|---|
| 智能体犯了一次错误 | 在 L0 或 L1 加一行 |
| 同一类错误再次出现 | 把这个修复变成一个 L2 skill |
| 它绝不允许再次出现 | 把它下推到一个 L4 hook |
| 它必须在无人查看的情况下被抓住 | 加一个 L5 检查 |
| 某起事故被调查 | 把可迁移的教训追加到该组件的 POSTMORTEM.md |

只有最后一行会自己触发自己。你无法跨会话看见，所以得由人来说「这是第二次了」。
当他们这么说时，就照这道阶梯来执行。

## 不变量（Invariants）

1. 只记录这个仓库里可观察到的、以及无法从代码推断出来的东西。绝不凭空捏造
   约定。
2. 只有当文件不存在时才创建它。如果它已存在，就发出一份 diff 然后停下。
3. 绝不整体重写一个文件，也绝不重复陈述它已经说过的东西。针对一个未改动的
   仓库再跑一次，必须不产生任何 diff。
4. 绝不编辑已有的 POSTMORTEM.md 条目。
5. 创建 L0 和 L1 文件。L2 到 L5 只做提议；由人来批准它们。
6. 不要提交（commit）。

## 流程（Procedure）

1. 盘点。把每一个已经存在的harness文件都读一遍：`/AGENTS.md`、组件的
   `AGENTS.md` 和 `POSTMORTEM.md`、`.claude/skills/*`、`.claude/agents/*`、
   hook、检查脚本、CI 工作流。下面你产出的一切，都是相对于这个基线的 diff。

2. 收集。阅读构建配置、CI 工作流、测试设置，以及最近改动过的三个目录。如果
   构建和测试开销不大，就各跑一次。提取出：无法从 manifest 猜出来的命令、与
   语言默认做法不同的选择、CI 里任何因为「曾经出过岔子」而存在的东西，以及
   顶层组件及其各自的职责。一个空仓库几乎产不出什么；最多问五个问题，然后就用
   你手上已有的东西继续。

3. 按照章节约定和预算写 L0 和 L1。在 `/AGENTS.md` 里加一行，声明它以及
   `.claude/skills/**` 是由人维护的，不得由智能体编辑。在一个新仓库里，「约定」
   可以是空的。

4. 提议 L2 到 L5。对每一项：给出路径、一行理由，以及内容。要覆盖：CI 或脚本里
   每一个重复出现的多步骤流程、每一条绝不允许被违反的「约定」规则、每一条脚本
   能够验证的「约定」规则，以及一个用于触发本 skill 的触发器（如果目前没有的
   话）。明确说明你把哪些规则挪出了自然语言，哪些留在原处。

5. 报告漂移（drift），但不修复其中任何一项：那些提到某个已不存在的文件、命令
   或 flag 的规则；那些步骤已不再与工具链匹配的 skill；那些没接到任何东西上的
   检查；那些体量已大到违背其自身用途的文件；那些陈述的是一个意图而非一个
   不变量的规则。

6. 待解决的问题。列出所有你靠猜测得出的东西，每项一行。

输出创建的文件、提议的 diff、漂移列表，以及待解决的问题。
