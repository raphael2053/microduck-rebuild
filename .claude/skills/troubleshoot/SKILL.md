# Troubleshoot

排查的核心是**假设循环**：提出假设 → 用证据验证 → 留下或丢弃 → 收敛 → 重复，直到根因被证据确认。**绝不臆测。**

## 用法

- `/troubleshoot 仿真启动即报 Actuator not found`
- `/troubleshoot 策略加载成功但鸭子站不住`

## 环境与可逆性

这个项目没有"生产环境"，但有**不可逆操作**。按此分级：

| 环境 | 可做什么 |
|---|---|
| **仿真 / 本地** | 随便试。跑挂了零成本，这是首选的实验场 |
| **上游仓库副本** | 只读。要改就在自己的副本里改，别改上游 clone |
| **实机硬件** | ⚠️ **上电、驱动舵机、打印、下单都不可逆**。动手前必须先在仿真里验证，且需用户明确同意 |

一条铁律：**能在仿真里复现的问题，绝不上实机排查。**

## Phase 0：定位

1. 读根 `AGENTS.md` —— 两条线的分工与全局约定
2. 读对应组件的 `AGENTS.md`（`software/` 或 `hardware/`）
3. 读该组件的 `POSTMORTEM.md` —— **先确认这是不是已知问题**
4. 读 `docs/open-questions.md` —— 是否已记录为未决项
5. 术语不熟就查 `docs/dictionary.md`，别猜

### 定位到哪条线

| 现象 | 组件 |
|---|---|
| 仿真、策略、训练、ONNX、依赖 | `software/` |
| 结构件、舵机、接线、供电、PCB | `hardware/` |
| 上游仓库本身的缺陷 | 记进 `docs/ecosystem.md`，postmortem 归对应线 |

## Phase 1：读代码

1. 找到出问题的那条调用路径，从入口读到失败点
2. 记下关键的函数名、常量名、文件名 —— 后面用它们做检索
3. ⚠️ **区分"我们的代码"和"上游的代码"**。这个项目大量依赖第三方仓库，多数问题出在接缝上而不是自己写的那几行

## Phase 2：假设循环

**循环，直到根因被 ≥2 个独立证据源确认。**

### 2.1 提出假设

- 一句话说清假设，例如「MJCF 里的 actuator 名字和代码里的对不上」
- 设计一个**具体的验证动作**：跑一条命令、读一段源码、做一次隔离实验
- 一次只验一个想法。复合假设会让你分不清确认了什么

### 2.2 取证

这个项目常用的证据源，**每种揭示的侧面不同**：

| 证据源 | 回答什么 | 怎么取 |
|---|---|---|
| **程序输出 / 退出码** | 它报了什么错，走到哪一步 | 直接跑，看完整 traceback |
| **隔离实验** | 把变量减到最少后还复现吗 | 例：不加任何控制的纯物理测试 |
| **源码与签名** | 接口到底长什么样 | `inspect.signature`、读安装后的库源码 |
| **模型元数据** | 这个模型文件真正要什么 | ONNX 的 `custom_metadata_map`、MJCF 的 actuator 名 |
| **文件本体** | 文件内容是不是名副其实 | 解包 `.3mf`、看预览图、比对零件名 |
| **上游 git 历史** | 这东西以前是什么样 | `git log --diff-filter=D`、`git show <commit>^:<path>` |
| **轨迹采样** | 过程中哪一步开始不对 | 每 N 步打印状态，而不是只看终值 |

**隔离实验是这个项目最有力的工具。** 把控制去掉只留物理、把策略换成常数、把一个参数置零 —— 每次只动一个变量。

### 2.3 判定

| 结果 | 动作 |
|---|---|
| 证据支持 | **KEEP** —— 记为已确认，继续收敛 |
| 证据反驳 | **DISCARD** —— 记为死胡同，写下学到了什么 |
| 证据不足 | **REFINE** —— 补证据，或把假设说得更具体 |
| 冒出意外信号 | **PIVOT** —— 跟着新信号走 |

### 2.4 记录

每轮都记，这直接变成 postmortem 的 Investigation Steps：

```
假设 #N：<一句话>
验证：<跑了什么 / 读了什么>
结果：<看到了什么>
判定：KEEP / DISCARD / REFINE / PIVOT
```

### 2.5 继续或收尾

- 根因被确认 → 退出循环，写 RCA
- **同一角度连续 3 次 DISCARD** → 退一步，换完全不同的方向
- 绝不停在「我觉得可能是……」

## Phase 3：根因总结

1. **一句话说清根因** —— 具体到哪个文件、哪行、哪个参数
2. **影响范围** —— 挡住了哪些阶段、是否影响 roadmap 的路线判断
3. **修法** —— 代码改动、换依赖版本、换方案
4. **回顾死胡同** —— 被证伪的假设同样值钱

### 检查清单

- [ ] 错误信息已定位到具体代码位置
- [ ] 根因是具体的，不是「哪里出了问题」
- [ ] 至少 2 个独立证据源
- [ ] 修法可执行
- [ ] 影响范围说清楚了

## Phase 4：Postmortem

写进 `software/POSTMORTEM.md` 或 `hardware/POSTMORTEM.md`。

**仅追加。绝不修改已有条目。** 新条目加在 `## 事故` 标题之下、旧条目之上（倒序）。

⚠️ **保持简洁。** 一条 postmortem 的价值在于让下一个人少走弯路，不在于记录得多全。

### 模板

```markdown
### YYYY-MM-DD：<标题>

**影响**：阻塞 / 降级 / 仅困扰
**环境**：仿真 / 本地 / 实机
**发现方式**：<怎么撞上的>

**现象**：<观察到什么>

**排查步骤**：

1. <查了什么、为什么查它>

   ```bash
   <命令>
   ```

   结果：<看到什么，与预期差在哪>

2. <继续>

**根因**：<具体到文件与行>
**影响范围**：<挡住了什么>
**修法**：<怎么解决的>
**预防**：<改了什么防止再犯>

**死胡同**（已证伪，别重走）：

- <假设> —— 因为 <证据> 被否

**可复用的验证手段**：

```bash
<命令，附一行说明它验证什么>
```
```

文件不存在就创建，用已有文件的头部格式。

## Phase 5：修复

根因确认后再动手。**用户说了只诊断就别改。**

1. **最小改动** —— 只碰导致根因的那部分
2. **先在仿真里验证**，再考虑实机
3. ⚠️ 涉及上游代码时，先判断是「我们用错了」还是「上游有 bug」。后者要记进 `docs/ecosystem.md` 并考虑提 issue
4. 验证方式：跑 `tools/checks/check-links.py`（文档类）、复现原始现象确认消失（代码类）

## Phase 6：自我演化

排查完检查有没有产生可复用的知识：

| 发现 | 放哪 |
|---|---|
| 新术语 | `docs/dictionary.md` —— **这是硬性约定**，见根 `AGENTS.md` |
| 上游仓库的缺陷或特性 | `docs/ecosystem.md` 对应条目 |
| 未决问题 | `docs/open-questions.md`，按阻塞程度排序插入 |
| 路线判断被推翻 | `docs/roadmap.md` |
| 组件级的坑 | 对应 `AGENTS.md` 的约定一节 |
| 值得机械拦截的规则 | 提议 L4 hook，见 `harness-review` skill |

提出更新，**经用户批准后再改**。

## 行为准则

1. **证据为王。** ≥2 个独立证据源才算确认。
2. **绝不臆测。** 验证不了就明说「未确认」。
3. **别原地打转。** 同一角度试 3 次没进展就换方向。
4. **小假设。** 一次一个想法。
5. **每轮都记。** 被否的假设也是知识。
6. **只读源码不算确认。** 代码解释「为什么」，但判定需要运行时证据。

## 反模式

- **只读代码就下结论** —— 必须有运行时证据佐证
- **一次改多个变量** —— 改好了也不知道是哪个起的作用
- **跳过 postmortem** —— 排查过的问题都要留条目，哪怕修法很简单
- **在实机上排查能在仿真里复现的问题** —— 成本和风险都高一个量级
- **把上游的缺陷当成自己的 bug 修** —— 先判断问题归属，否则会在错的地方越陷越深
